Design principles

Four rules that shaped every decision

01

Canonical business taxonomy controls classification.

02

Historical handling evidence influences priority and confidence.

03

Deterministic rules stay deterministic — no model call where the data already answers exactly.

04

Uncertainty leads to human review, not hidden guessing.

Every automated decision is backed by either the organization's taxonomy or historical handling evidence; disagreement becomes uncertainty.

Architecture

One local prototype, one linear workflow

Why LangGraph

Why LangGraph — and what it isn't doing here

  1. Explicit ordered stages, not an implicit convention buried in a function
  2. One shared, typed state object every node reads and writes
  3. Deterministic and model-driven steps coexist cleanly
  4. Intermediate state is inspectable and independently testable
  5. The workflow can grow without turning into one giant function

The production graph is linear — one edge after another. Retry/fallback is control flow inside the classification node. Escalation is a decision computed in the final node. No conditional graph branches exist today.

LangGraph was appropriate because the case study specifies a multi-stage workflow whose intermediate decisions matter — not because every classifier needs a graph.

Classification & routing

Constrained classification, deterministic routing

Classification

  1. Complete taxonomy injected into the prompt
  2. Pydantic / Literal-constrained output — only a valid category can come back
  3. qwen2.5:1.5b-instruct
  4. One retry on unusable structured output
  5. Deterministic taxonomy fallback, which always forces escalation

Confidence & escalation

An evidence score, not a calibrated probability

Strongest single retrieved similarity.

Category agreement

Similarity-weighted share of neighbors matching the predicted category.

What the evaluation taught us

Three findings that shaped the final design

1 — Classification > priority

80.33% vs. ~56%. Classification is the strong link; priority inference from neighbor voting is the weak one.

2 — Weighting added nothing

Similarity-weighted priority matched plain majority vote on all 300 held-out cases — added complexity, zero benefit.

3 — Similarity alone is a poor confidence signal

Composite evidence is more usable for selective escalation, but still not a calibrated probability.

Priority quality, not routing architecture, is the main bottleneck.

Limitations & roadmap

What this is — and what it would take to ship

Limitations

  • 300 synthetic/curated cases
  • Priority signal weak, especially medium
  • One taxonomy, one chat model, one embedding model
  • Confidence not calibrated
  • Small local model can occasionally transfer details from a highly similar retrieved historical case into a generated response, despite grounding instructions
  • No real customer outcomes
  • Resolution quality lacks human production labels

Roadmap

Data / ML

  • Collect reviewer corrections and real outcomes
  • Improve the priority signal
  • Calibrate confidence
  • Monitor category / data drift

Engineering

  • API / service boundary
  • CRM / ticket integration
  • Observability
  • Human-feedback capture

Optional downstream automation: finalized triage results can trigger internal notifications through n8n, while operational automation remains separate from the LangGraph reasoning workflow.

Summary

Four takeaways

Taxonomy-constrained classification

Evidence-grounded historical retrieval

Deterministic routing where business rules are deterministic

Measured uncertainty with human escalation

Prototype complete; production deployment would require better priority evidence and confidence calibration on real operational data.
